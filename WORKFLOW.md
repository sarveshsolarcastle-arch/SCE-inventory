# Operating Workflow — from a closed deal to a completed installation

Last updated: 2026-09-08. Written for a three-person team: **Admin**, **Finance A**, **Finance B**.

This is the operating manual, not a feature list. It says who does what, in what order, on
which screen, and what has to be true before the next person can start. Where the workflow
depends on something the app does **not** model, that is called out rather than glossed over
— see §13.

Reasoning is kept in collapsed **"Why"** blocks. Read the steps; open a block only when you
want to know why the rule is what it is.

---

## 1. The three people, and what the system actually enforces

| Person | System role | Holds |
|---|---|---|
| **Admin** | `ADMIN` | Everything. Approvals, accounts, backups, reversals, adjustments, sites, shelves. |
| **Finance A** — inbound, audit, clerical | `FINANCE` | Deliveries, items, defects, dispatch + challan, all stock movement, ledger. |
| **Finance B** — site work | `FINANCE` | **Identical to Finance A.** |

### Read this before anything else

**Finance A and Finance B are the same role.** The system has two roles, not three. There is
no permission that A holds and B does not, or the reverse. The A/B split described in this
document is an **agreement between people**, not a rule the software applies.

What the software *does* give you is **attribution**: every `Transaction`, `Dispatch`,
`Delivery` and `SitePickup` row carries the `userId` of whoever created it, permanently. So
you can always answer *"who booked this?"* after the fact — you just cannot stop the wrong
person doing it beforehand.

Two consequences, and both are load-bearing:

- **This is a feature when someone is away.** B can cover A's goods receipt on a sick day
  without an admin unlocking anything. Do not try to "fix" the shared role with a third
  account; the client already retired one role for exactly this reason.
- **It means separation of duties is a review control, not a gate.** The compensating control
  is the attribution review in §10.3. Skip that and the split is nothing but habit.

**Admin sits in the path of exactly five things**, and nothing else in daily operations:

`site:manage` · `shelf:manage` · `shelf:delete` · `stock:reverse` · `stock:adjust`

Finance may **request** all five through the approval queue. Two capabilities —
`user:manage` and `backup:manage` — are requestable by **nobody**, by design, permanently.
Do not add them: an approval flow that can mint an admin is not an approval flow, and an
approved database restore would delete the very row that authorised it.

```

        |
  [2] Site created         Finance A  ->  Admin approves
        |
  [3] Procurement          Admin decides  PARTLY outside the app
        |
        +---- to store ----+              +---- direct to site ----+
        |                  |              |                        |
  [4] Goods receipt        Finance A      Finance A                |
  [5] Defect claims        Finance A / Admin                       |
        |                  |                                      |
  [6] Dispatch + challan   Finance A --- hands over --> Finance B  |
        |                                                         |
  [7] At site: consume / transfer / return / pickup  <-------------+
        |                  Finance B
  [8] Monthly audit        Finance A, reviewed by Admin
        |
  [9] Close-out            Finance B + Finance A -> Admin signs off
```

## 3. Stage 1 — Deal closed

**This happens outside this system, and no role in the app owns it.** The app has no CRM, no
quotation and no order record. Closing a deal is not something it does, and nothing in this
document assigns it.

What matters here is only what has to **reach Finance A** before Stage 2 can start: a **site
brief** carrying five fields. They are exactly what the app needs and exactly what the printed
challan depends on.

| Field | Goes to | Why it matters |
|---|---|---|
| Site name | `Site.name` | Internal label; appears in every dropdown. |
| Short location | `Site.location` | Kept short **on purpose** — it renders inside `<select>` menus. Not the postal address. |
| Customer / party name | `Site.customerName` | Prints as the challan's "Delivery Challan For". Falls back to site name if blank. |
| Full postal address | `Site.address` | The multi-line address printed on the challan. This is why it is separate from `location`. |
| Client's project code | `Site.projectCode` | Prints as Project ID. It is **their** numbering, free text, not generated by us. |

Also useful in the brief, though the app does not store it: the bill of materials, target
install date, and site contact. Keep these wherever they live today (see §13, gap 2).

**Done when:** Finance A has the five fields in writing.

## 4. Stage 2 — Site created

**Owner: Finance A. Approver: Admin.**

1. Finance A opens **`/sites/new`** and fills the five fields.
2. On submit, because `site:manage` is *requestable* but not *held*, this does **not** create
   the site. It raises an `ApprovalRequest` and lands Finance A on `/approvals`.
3. Admin opens **`/approvals`**, reads the server-built summary, and approves.
4. The site is created **attributed to Finance A**, not to the approving admin.

Two working rules that follow from this:

- **Admin clears the approval queue twice daily** — start of day and mid-afternoon, at fixed
  times, so Finance can plan around them.
- **For an urgent site, Admin creates it directly** at `/sites/new` under their own login.
  Admin holds `site:manage` outright, so it is created immediately with no request.

<details>
<summary><strong>Why — the scheduling cost of a slow approval</strong></summary>

Nothing downstream can happen until this approval lands. No dispatch, no direct-to-site
delivery, no site page. A deal that closes on Friday evening and an admin who checks the queue
on Monday costs the project a working day before any material can legitimately move. That is
the whole reason for the fixed twice-daily sweep and the direct-creation escape hatch.

</details>

Later corrections to the address, customer name or project code go through `/sites/[id]` and
are the same request-and-approve loop (`site.update`). **Get the address right the first
time** — a wrong address discovered while a driver is waiting means an approval round trip.

**Done when:** the site exists and its page loads at `/sites/[id]`.

## 5. Stage 3 — Procurement

**Owner: Admin decides. Finance A executes and records.**

The app does not model purchase orders (see §13, gap 3). What it *does* give you is the
information to decide with, and the record of what arrived.

### 5.1 What to buy

Finance A prepares the ask from:

- **`/items`** — low-stock flags, driven by each item's `minStock`.
- **`/dashboard`** — totals, low-stock alerts, recent movement.
- **`/at-sites`** — material already sitting at other sites. **Check this before ordering.**
  A transfer from a finishing site is cheaper than a purchase, and the app supports it
  natively (§9.2). This is the single habit that saves the most money in the workflow.
- The BOM from the site brief.

Admin approves the spend and raises the purchase order in whatever system the company uses
today.

### 5.2 The one decision that is durable — where it gets delivered

Decide this **at PO time**, with the supplier, because it determines how the arrival is
recorded and it is awkward to change afterwards:

| | **To the store** | **Direct to site** |
|---|---|---|
| Typical material | Cable, fasteners, consumables, connectors, anything shared across projects | Panels, mounting structure, inverters — bulky, project-specific, single-use |
| Recorded as | `Delivery` with **no site** | `Delivery` with **the site set** |
| What the ledger does | `STOCK_IN` — packs land in the store | `STOCK_IN` **and** an immediate `ISSUE` to that site, sharing one delivery ID |
| Net effect at the office | Stock increases | Nets to zero. The material never touches a shelf. |
| Where it shows up | `/items`, `/shelf` | The site's holdings at `/sites/[id]` |
| Requires | Nothing | **The site must already exist** — i.e. Stage 2 must be approved |

<details>
<summary><strong>Why — the paired stock-in and issue is deliberate</strong></summary>

A direct-to-site delivery writes two transactions per line rather than a dedicated
"site delivery" type. That is not bookkeeping sleight of hand: it means site balances, the
return guard, the dashboards and every site page keep working with no special case. A separate
transaction type would have meant editing every one of them, with a chance of missing one. The
UI reads the shared delivery ID and renders the pair as a single event.

</details>

**Done when:** the PO is placed and the destination is agreed in writing with the supplier.

## 6. Stage 4 — Goods receipt

**Owner: Finance A.** Screen: **`/deliveries/new`**.

1. **Count against the supplier's challan before signing it.** This is the only moment a
   discrepancy is cheap to raise.
2. Record the delivery: supplier, their challan/invoice number into **`reference`**, date,
   and the site if this is a direct-to-site delivery.
3. One line per item, entered as pack size × pack count (e.g. 4 rolls × 400 m), not as a raw
   total. The app converts to base units itself.
4. **Anything damaged on arrival goes in as a defective quantity on the same line**, not as
   good stock. It becomes a `DefectiveItem` with source `DELIVERY`, status `QUARANTINED`.
   Quarantined goods physically exist but are **not stock** and cannot be issued.
5. **Put away:** assign the packs to shelf boxes at **`/shelf`**. Fresh sealed stock goes in
   `FRESH` boxes. `/shelf/suggestions` recommends moving high-movement items to more
   accessible positions — worth acting on when the arrival is large enough to justify a
   reshuffle.
6. **File the paper challan under the reference number you typed.** That number is the only
   join between this row and the paper.

**Done when:** stock totals on `/items` match the physical count, and the paper is filed.

## 7. Stage 5 — Defective goods and supplier claims

**Owner: Finance A raises and records. Admin chases the supplier commercially.**

Screen: **`/defective`**. Three states, and they only move forward:

1. **`QUARANTINED`** — set automatically when the defect is recorded, whether it arrived
   damaged (§6) or came back damaged from a site (§9.3).
2. **`CLAIMED`** — Finance A moves it here when the claim actually goes to the supplier.
   Not before. This state means "we have asked".
3. **`REPLACED`** — set when the replacement arrives. Record the replacement as a normal
   delivery first, then link it; the row records **which** delivery made good on the claim,
   so an unfulfilled claim is a query rather than someone's memory.

**Cadence:** raise the claim as soon as the defect is recorded — do not wait for the audit.
The **ageing check is one of the four monthly reviews** (§10.2): anything `QUARANTINED` for
more than 30 days either becomes `CLAIMED` or gets a note explaining why not, and anything
`CLAIMED` for more than 60 days goes on Admin's list.

## 8. Stage 6 — Dispatch to site, and the challan

**Owner: Finance A (recording and paperwork). Finance B (physical handover onward).**

Screen: **`/dispatches/new`**.

1. Pick the site. Enter lines, or **paste the block straight from Excel** — the form parses a
   pasted table, which is what the whole batch dispatch feature exists for.
2. **Opening a sealed pack requires an explicit confirmation in the same request.** If the
   quantity needs a sealed pack broken open, the form says so and Finance A confirms. This is
   a same-person handshake, unrelated to Admin approvals.
3. **Continuous material must come from a single pack.** 60 m of wire cannot be assembled
   from three 20 m offcuts, and the allocator will refuse rather than pretend. Discrete
   material (screws, connectors) pools freely.
4. **Check the lines before saving. A dispatch cannot be edited afterwards.**
5. Save. The dispatch gets a **challan number automatically** — unique, gap-free, allocated by
   a counter inside the same transaction. **It cannot be typed, edited, or reused.**
6. Print at **`/dispatches/[id]/challan`**.
   - `deliveredBy` / `receivedBy`: fill them in if the driver and site contact are known;
     leave blank and they print as **ruled lines to sign by hand**.
   - Print **two copies**: one travels with the material and comes back signed, one is filed
     immediately.
   - Fully reversed dispatches will not print, and reversed lines are omitted from a partly
     reversed one. That is deliberate.

<details>
<summary><strong>Why — what a mis-keyed dispatch actually costs</strong></summary>

There is no edit. A mistake has to be *reversed* (`stock.reverseDispatch`), and Finance can
only **request** a reversal — so a typo costs an approval round trip. If the challan is already
out, it also leaves a document in the field that no longer matches the ledger, and the
replacement carries a different challan number. Catching it before saving costs nothing;
catching it after costs all of that.

</details>

**The handover point.** Once Finance A hands the material and the challan to Finance B or the
driver, responsibility for that material transfers to Finance B. The signed copy coming back
is the evidence it arrived.

**Done when:** the challan is printed, the material has left, and the office copy is filed.

## 9. Stage 7 — At site: installation and material management

**Owner: Finance B.** Screens: **`/sites/[id]`** for one site, **`/at-sites`** across all of
them. The app is mobile-responsive; this is meant to be done from a phone, on site.

A site's holdings are **derived** — everything sent, plus transfers in, minus returns,
consumption and transfers out. If Finance B never books consumption, that list grows forever
and stops describing what is actually there. **Booking consumption is not paperwork; it is
what makes the site page true.**

### 9.1 Consume — material actually installed

Book `CONSUME` as material is used, **daily, from site — not in a batch at the end of the
job.** A week-old memory of how much cable went onto a roof is a guess. Consumption has zero
effect on store stock (the material left the store when it was issued) and reduces the site's
holding.

### 9.2 Transfer — material moving site A → site B

When surplus goes straight from one site to another without returning to the store, record a
`TRANSFER`, not a return-plus-reissue. It records both origin and destination and touches no
packs at all — packs are a store-side concept, and this material never goes near a shelf.
**Check `/at-sites` before ordering anything (§5.1); this is the action that saves the money.**

### 9.3 Return — material coming back to the store

Record a `RETURN`. If part of what came back is damaged, **split it on the same line** using
the defective quantity — the good part restocks, the damaged part quarantines as a
`DefectiveItem` with source `RETURN` and enters the claim flow in §7. Returned packs go back
onto the shelf; opened packs keep their individual remainder, because a 30 m offcut and a 50 m
offcut are not interchangeable.

### 9.4 Pickup flag — material stranded at site

For material that is neither in use nor consumed — a remainder too small, or a site too far,
to be worth a trip right now — **flag it for pickup**. The flag *labels* the material; it
never moves it. The material stays company property and stays on the site's books.

<details>
<summary><strong>Why — the accident this prevents</strong></summary>

If consumption were the only way to clear a site's list, someone tidying up will eventually
book stranded material as consumed — writing off wire that is sitting on a roof, entirely
retrievable. That is a real write-off of real material, caused by tidying. Flagging it labels
the material instead, keeps it on the books, and lets it be collected when someone is next
heading that way.

</details>

### 9.5 Finance B's site rhythm

| When | Do |
|---|---|
| Before leaving site, every day | Book the day's `CONSUME` lines |
| When surplus is identified | Decide: return, transfer, or pickup-flag. Never leave it undecided. |
| On return to the office | Hand the signed challan copy to Finance A |
| Weekly | Walk `/at-sites` and confirm each site's list matches what is physically there |

## 10. Stage 8 — Monthly audit and reconciliation

**Owner: Finance A. Reviewed by Admin.** Suggested slot: the first working week of the month.

This is the one substantial audit. The daily and weekly work above is operational; this is
where the books get checked against reality.

### 10.1 Spot count

Physically count **three or four high-movement items** and compare against `/items`. If they
disagree, record a stocktake adjustment. Finance can only **request** `stock:adjust`; Admin
approves at `/approvals`.

Every adjustment carries a mandatory reason. Corrections stay visible instead of being
disguised as fake issues — that is the point of the type existing.

<details>
<summary><strong>Why — a delayed approval is safe, and this is worth understanding</strong></summary>

The request carries the **ledger figures that were on screen at the time of the count**, not
just the counted total. So what gets applied is a *correction of known size*, which survives
legitimate movement between counting and approving. Counting on the 3rd and approving on the
5th applies the right correction, not a stale total — which matters precisely because this is
now a monthly cycle and a request may sit for a day or two.

</details>

### 10.2 The four monthly reviews

| Review | Screen | Looking for |
|---|---|---|
| **Stale site material** | `/at-sites` | Anything at a site with no movement for a month. Chase Finance B for a consume / return / pickup decision. |
| **Defect ageing** | `/defective` | `QUARANTINED` > 30 days, `CLAIMED` > 60 days (§7). |
| **Challans outstanding** | Paper file vs `/dispatches` | Dispatches with no signed copy returned. |
| **Attribution** | `/dispatches`, `/deliveries`, site pages | Movements booked by the person who did *not* do them — see below. |

### 10.3 The attribution review — the compensating control

Because Finance A and Finance B hold identical permissions (§1), **this review is the only
thing standing in for separation of duties.** Admin scans the month's ledger and asks a single
question: *does the person recorded against each movement match who actually did it?*

Cover during absence is legitimate and expected. A pattern of B routinely booking goods
receipt, or A routinely booking site consumption, is not cover — it means the split has
quietly stopped existing, and this review is where you find that out.

## 11. Stage 9 — Installation complete and close-out

**Owner: Finance B does the material work, Finance A the paperwork, Admin signs off.**

Work the checklist in order. Steps 1–3 must all be true before the site is considered closed.

| # | Check | Owner | Screen |
|---|---|---|---|
| 1 | Everything installed is booked as `CONSUME` | Finance B | `/sites/[id]` |
| 2 | All surplus is decided: returned, transferred to the next site, or pickup-flagged **with a collection date** | Finance B | `/sites/[id]` |
| 3 | **Site holdings read zero**, or show only pickup-flagged lines | Finance B | `/sites/[id]` |
| 4 | Every dispatch has a signed challan copy in the file | Finance A | paper vs `/dispatches` |
| 5 | Damaged returns are quarantined and claimed | Finance A | `/defective` |
| 6 | Review and sign off | **Admin** | `/sites/[id]` |

### The site is not deleted

`deleteSite` refuses on any site that has transactions, dispatches, deliveries, defect records
or pickups against it. **There is no "closed" status field either**, so agree a convention and
hold to it: **rename the site to `[CLOSED] <name>`** on sign-off, so every dropdown sorts
closed sites away from live ones, and put the sign-off date in `notes`.

A rename is normally a `site.update` request. Since Admin is signing off anyway, the practical
move is for **Admin to make the rename directly** as the act of signing off. One person, one
action, no queue.

<details>
<summary><strong>Why — a completed project is kept, permanently</strong></summary>

Deleting a completed site would punch a hole in the accountability trail this system was built
to provide: every dispatch, delivery and consumption row against it would lose the thing it
points at. The refusal is deliberate and should not be worked around. A completed site stays
as its own history — the `[CLOSED]` convention exists only to keep it out of the way, not to
hide it.

</details>

## 12. Admin's standing duties

| Duty | Cadence | Screen |
|---|---|---|
| Clear the approval queue | **Twice daily**, at fixed times | `/approvals` |
| Create urgent sites directly | As needed — beats waiting for a request | `/sites/new` |
| Approve reversals and adjustments | Within the queue sweep | `/approvals` |
| Verify the nightly backup ran | Weekly | `/backups` |
| Review the audit; attribution review | Monthly | §10 |
| Accounts: create, deactivate, reset passwords | As needed. **Never delegated — not requestable by anyone** | `/users` |
| Backup restore drill | Quarterly | `/backups` |

### The approval queue in full

Eleven operations Finance may request. Everything else Finance does is immediate.

| Operation | Raised by | Typical trigger |
|---|---|---|
| `site.create` | Finance A | A new site brief has arrived (§4) |
| `site.update` | Finance A | Wrong address / customer name on a challan; close-out rename |
| `site.delete` | Finance A | Site created in error, before any material moved |
| `shelf.create` | Finance A | New racking installed |
| `shelf.delete` | Finance A | Racking removed |
| `shelf.slot.boxType` | Finance A | Box repurposed Fresh → Opened → Recyclable |
| `shelf.slot.item` | Finance A | Item reassigned to a different box |
| `shelf.slot.frontRow` | Finance A | Acting on a placement suggestion |
| `stock.reverseTransaction` | Either | A single movement booked in error |
| `stock.reverseDispatch` | Finance A | A whole dispatch booked in error (§8) |
| `stock.adjust` | Finance A | Physical count disagrees with the ledger (§10.1) |

<details>
<summary><strong>Why — two things about approvals that are easy to assume wrongly</strong></summary>

**Approving runs the operation.** It does not merely unlock a button for Finance to press
later. The work is done immediately, and recorded against the **requester**, not the approver.

**A request whose preconditions have changed by approval time fails cleanly.** Nothing
half-happens: the status write and the work share one transaction, so a rollback takes both,
and the refusal reason is recorded on the row.

</details>

## 13. What this workflow depends on that the app does not model

Named honestly, with the workaround that holds today and what a fix would cost.

| # | Gap | Consequence | Workaround today | Fix |
|---|---|---|---|---|
| 1 | **No deal or order record** | The customer, value and scope of the job live outside the system entirely. **The app plays no part in closing a deal.** | The site brief (§3) | Out of scope — that is a CRM, not an inventory system |
| 2 | **No bill of materials per site** | You **cannot ask "is this site over-consuming against plan?"** — only "what has it received and used". The most valuable missing report. | Keep the BOM alongside the brief; compare by eye against `/sites/[id]` | A `SiteRequirement` model plus a planned-vs-actual panel. Moderate schema change. |
| 3 | **No purchase orders** | Nothing records what was **ordered and not yet received**. There is no "awaiting delivery" view, and a supplier three weeks late is invisible to the app. | Track POs outside; the delivery's `reference` field is the join back | A `PurchaseOrder` model that deliveries settle against |
| 4 | **No site status / archive** | Completed sites sit in every dropdown forever | The `[CLOSED]` naming convention (§11) | A `status` field on `Site` and a filter on the list. **Small change, high daily value.** |
| 5 | **No costing anywhere** | No item has a price. The challan prints no rates, and no report can value stock on hand or material consumed on a job. | Value externally from purchase invoices | A rate on `Item` plus a valuation report. Larger than it looks — it raises which cost basis to use. |
| 6 | **No labour or scheduling** | Install dates, crew and progress are not tracked | Whatever is used today | Out of scope |
| 7 | **Finance A / B not separable** (§1) | Separation of duties is a review, not a gate | The attribution review (§10.3) | Deliberate, and probably correct for a three-person team. Do not "fix" it without a reason. |

## 14. The rhythm, on one page

| | Finance A | Finance B | Admin |
|---|---|---|---|
| **Daily** | Record arrivals; put away; dispatch + challan; file paper | Book consumption from site; decide surplus | **Clear the approval queue, twice** |
| **Weekly** | Raise any outstanding supplier claims | Walk `/at-sites`; confirm each site matches reality | Verify the nightly backup ran |
| **Monthly** | **The audit** — spot count and the four reviews (§10) | Clear whatever the stale-material review turns up | Review the audit; approve adjustments; **attribution review** |
| **Per deal** | Create the site (§4); order and receive (§5–6) | Deliver, install, close out material (§9, §11) | Approve the site; approve the spend; **sign off close-out** |
| **Quarterly** | — | — | Backup restore drill |
